# Activity 3 – Apache Flink: Real-Time Patient Vital-Sign Monitoring

> **EDUCATIONAL DEMONSTRATION ONLY.** All patient data is **synthetic** (generated by
> `patient_model.py`). All thresholds are **illustrative teaching values, not clinical
> diagnostic criteria**. This system must not be used for patient care.

## What it does
Ten simulated bedside monitors stream heart rate, SpO₂ and body temperature (one reading every
5 s of event time, 10:00–12:00, 14,400 readings). Readings travel through Kafka and are delivered
**out of order** (as real networks do). One PyFlink job processes the stream in **event time** and
produces four continuous outputs: reading alerts, sustained-episode alerts (onset and resolution),
5-minute per-patient summaries and 15-minute ward summaries.

```
patient_model.py ──► vitals_producer.py ──► Kafka topic patient-vitals (2 partitions, key=patient)
 (seed 11, ground     (sends in ARRIVAL order:                     │
  truth, delays)       ~10 % out of order, 66 very late)           ▼
                                   ┌───────────── Flink 1.20.5 session cluster (Docker) ─────────────┐
                                   │ JobManager (768 MB)        TaskManager (1152 MB, 2 slots)        │
                                   │ Source: Kafka, WATERMARK = event_time − 30 s                      │
                                   │  ├─ Q1 filter ─────────────────────────────► vital-alerts         │
                                   │  ├─ unpivot → OVER(ROWS 11 PRECEDING) score                        │
                                   │  │     ├─ Q2 MATCH_RECOGNIZE (L M* S) ────► episode-alerts (ONSET)│
                                   │  │     └─ Q3 MATCH_RECOGNIZE (L M* S X* R) ► episode-alerts (RESOLVED)
                                   │  ├─ Q4 TUMBLE 5 min per patient ──────────► patient-summaries     │
                                   │  └─ Q5 TUMBLE 15 min ward ────────────────► ward-summaries        │
                                   │ checkpoints every 10 s                                             │
                                   └────────────────────────────────────────────────────────────────────┘
                                                        │
                                   results_collector.py ─► results/*.csv ─► evaluate.py, charts.py
```

## Educational thresholds and rules (`thresholds.json`)
| Item | Value |
|---|---|
| Heart rate abnormal | > 120 or < 50 bpm |
| SpO₂ abnormal | < 92 % |
| Temperature abnormal | > 38.0 °C or < 35.5 °C |
| Episode score | abnormal readings among the last 12 of that patient+vital (= 60 s) |
| Episode onset / resolved | score ≥ 9 / score ≤ 3 (hysteresis) |
| Watermark | event time − 30 s (bounded out-of-orderness) |
| Windows | 5-min tumbling per patient; 15-min tumbling for the ward |

## Run it (project root, PowerShell)
```powershell
.venv\Scripts\python.exe activity3_flink\patient_model.py          # data + ground truth
docker build -t bigdata/pyflink:1.20.5 activity3_flink              # once, ~1 GB image
docker compose --profile flink up -d                                # kafka + jobmanager + taskmanager
powershell -ExecutionPolicy Bypass -File activity3_flink\setup_topics.ps1
docker exec flink-jobmanager flink run -d -py /opt/activity3/vitals_job.py
# two terminals:
.venv\Scripts\python.exe -u activity3_flink\results_collector.py --idle-exit 40
.venv\Scripts\python.exe -u activity3_flink\vitals_producer.py --speed 30   # 2 h of data in ~4 min
.venv\Scripts\python.exe activity3_flink\evaluate.py
.venv\Scripts\python.exe activity3_flink\charts.py
docker exec flink-jobmanager flink list ; docker exec flink-jobmanager flink cancel <job-id>
docker compose --profile flink down
```
Flink Web UI: http://localhost:8081 (job graph, watermarks, back pressure, checkpoints).

## Technical decisions (viva notes)
1. **Why Flink and not just Kafka consumers?** Kafka only transports and stores events. Event-time
   ordering, watermarks, windowed aggregation, stateful sliding scores, pattern matching (CEP) and
   checkpointed state are Flink features; here they run inside the Flink TaskManager.
2. **Event time + watermark.** 1,420 readings arrive out of order (5–25 s) and 66 very late
   (45–150 s). With a 30 s bounded-out-of-orderness watermark, the out-of-order ones are re-ordered
   correctly; the very late ones are dropped by time-based operators, which we measured exactly.
   The stateless alert filter does **not** depend on the watermark, so even late readings are alerted.
3. **Why a 9-of-12 score instead of "12 consecutive".** Found before any Flink run: with realistic
   noise, P09's bradycardia (≈46 bpm vs 50 threshold) never stays below 50 for 12 readings in a row,
   so a strict-run rule would miss it. The OVER-window score tolerates noise; the 9/3 hysteresis
   prevents alert flapping (score dips to 7–8 inside the episode without resolving it).
4. **P05's transient burst (8 readings) is a deliberate edge case**: it peaks at score 8 — one short
   of the onset rule — so it produces 8 reading alerts but no episode alert.
5. **Two-phase window aggregation.** Flink pre-aggregates windows inside the source task
   (`LocalWindowAggregate`), so the global window operators received only 722 and 82 records.
6. **End-of-stream markers.** A watermark is the minimum across partitions, and the last windows
   only close when the watermark passes them. The producer sends one `__EOS__` record per
   partition with a later event time; the job filters it out before any processing.
7. **Latency trade-off.** Stateless alerts: ~45 ms. Anything ordered by event time must wait until the
   watermark passes (30 s of event time = 1 s wall clock at 30× speed) → ~1.3 s.
8. **Watermark shown in the UI as 5:44:25 pm** = 12:14:25 UTC event time rendered in IST.

## Issues found and fixed (documented, not hidden)
1. **Quadratic CEP pattern → back pressure (run 1, superseded).** The first RESOLVED pattern
   `(S X* L)` started a new partial match at every high-score row. During P06's ~58-minute fever
   (~690 rows) per-row work grew quadratically: `Match` busy = 100 %, upstream back pressure "high",
   watermarks stalled, and the fever-resolution event was missing 4 minutes after input ended.
   Fixed by anchoring the pattern at a calm row: `(L M* S X* R)` → one partial match per episode.
   Run 1 evidence kept in `evidence/act3/run1_superseded_backpressure/` (not used for results).
2. **Producer pacing race** at 300× test speed (negative `sleep`) – fixed by computing the wait once.
3. **Stale REST metrics.** The Web UI metric fetcher returned zeros/old counts right after start-up;
   a snapshot taken then was discarded. Final counts were read after the job was idle.
4. **PowerShell wildcard bug** in my capture script: `-like '...[22]*'` treats `[22]` as a character
   class, so two "vertex" screenshots actually showed the job overview; they were deleted/renamed and
   recaptured with exact matching.
5. **pandas 3 timestamp resolution** made the first latency numbers nonsense (epoch-sized); fixed with
   an explicit millisecond conversion before any result was recorded.
6. **Per-subtask metric store** (e.g. `numLateRecordsDropped`) returned no data in this Docker setup,
   so late-data drops are measured from operator I/O counts and outputs instead.

## Limitations and possible improvements
* Synthetic signals with simple noise; no artefact detection beyond the score rule.
* Fixed population thresholds; real monitoring would use patient-specific baselines and clinically
  validated early-warning scores (out of scope and not attempted here).
* Very-late readings are dropped by windows/CEP; could be routed to a side output or handled with
  allowed lateness in the DataStream API.
* Single TaskManager, parallelism 2, local filesystem checkpoints; production would use a
  replicated state backend (e.g. RocksDB + S3/HDFS) and exactly-once Kafka sinks.
